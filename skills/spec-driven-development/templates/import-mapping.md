# Deterministic Import Mapping

This is the rule table for `/spec import`. The importer is mechanical: it matches source headings against this table (case-insensitive, anchored at heading start), copies content **verbatim** into the matching target section, and routes everything else to `imported/source-excerpts.md` flagged `[UNMAPPED]`.

The importer MUST NOT:
- Paraphrase source text.
- Merge items across source headings.
- Invent FR / SC / US / Task IDs that did not exist in the source (use `FR-001`, `FR-002`, … in source order if no IDs were assigned).
- Invent priorities (P1/P2/…) — every imported user story is unprioritised; engineer assigns priorities in `/spec clarify`.
- Invent Independent Tests — every imported user story gets `Independent Test: [NEEDS CLARIFICATION: imported from <source>; engineer must define]`.
- Apply defaults from `docs/spec/defaults.md` during import — defaults are applied during a follow-up `/spec specify --use-defaults` pass, not during import.
- Make any judgement about quality or completeness — that's spec-challenger's job after import.

## Heading Mapping (case-insensitive, regex anchored at start of heading text)

| Source heading regex | Target |
|----------------------|--------|
| `^(overview\|summary\|background\|problem\|context\|introduction)$` | `spec.md §Summary` (free-form prose, copied verbatim) |
| `^(user stor(y\|ies)\|stories\|personas\|use cases\|user flows\|user journey)$` | `spec.md §User Scenarios & Testing` (one User Story per top-level item; nested items containing `given`/`when`/`then` or `should`/`must` become Acceptance Scenarios; everything else under each story is appended verbatim under the story bullet) |
| `^(functional[ -]?)?requirements?$\|^features?$\|^capabilities$\|^functional spec(ification)?$` | `spec.md §Functional Requirements` (one FR-NNN per bullet/numbered item; preserve source IDs if present) |
| `^(success criteria\|goals\|kpis\|metrics\|outcomes\|definition of done)$` | `spec.md §Success Criteria` (one SC-NNN per item) |
| `^(edge cases?\|errors?\|failure modes?\|what if|exception(al)? cases?)$` | `spec.md §Edge Cases` |
| `^(assumptions?\|prerequisites)$` | `spec.md §Assumptions` |
| `^(constraints?\|limitations?)$` | `spec.md §Assumptions` (with `[CONSTRAINT]` prefix) |
| `^(dependencies\|integrations?\|external (services?\|systems?))$` | `spec.md §Dependencies` |
| `^(out of scope\|non[- ]goals\|excluded)$` | `spec.md §Out of Scope` |
| `^(architecture\|design\|technical approach\|technical design\|implementation\|how it works)$` | `plan.md §Summary` (prose) and `plan.md §Technical Context` (any structured table or list with tech names — split by simple heuristic: bulleted "X: Y" pairs go to Technical Context table; prose to Summary) |
| `^(data model\|schema\|entities\|database\|domain model)$` | `plan.md §1.1 Data Model` (and copy entity names without fields to `spec.md §Key Entities`) |
| `^(api\|api design\|contracts?\|endpoints?\|interfaces?\|protocols?)$` | `plan.md §1.2 Interface Contracts` |
| `^(security\|auth(entication\|orisation)?\|permissions?\|access control)$` | `plan.md §1.3 Security` |
| `^(observability\|logging\|metrics\|monitoring\|telemetry\|alerting)$` | `plan.md §1.3 Observability` |
| `^(reliability\|resilience\|failure handling\|retry\|fallback)$` | `plan.md §1.3 Failure Modes` |
| `^(test(ing)?( plan)?\|qa\|quality)$` | tasks.md `## Source Test Plan` appendix (appended verbatim; NOT auto-converted to test tasks — test tasks are generated from FRs in Phase 4) |
| `^(tasks?\|todo\|to[- ]do\|implementation steps\|phases\|milestones\|breakdown\|wbs)$` | tasks.md tasks (each line gets a `T###` ID; checkbox lines `- [ ]` and numbered lines `1.` map 1:1; un-prefixed bullets are imported but flagged `[NEEDS REVIEW]` because they may not be tasks) |
| `^(risks?\|known issues?)$` | `imported/source-excerpts.md` under `## Risks` (engineer triages — risks are not a first-class spec section) |
| Anything else | `imported/source-excerpts.md` under a heading naming the source section, prefixed with `[UNMAPPED]` |

## Source Format Detection

The importer dispatches by source path / extension:

| Source | Detection | Notes |
|--------|-----------|-------|
| `docs/plans/YYYY-MM-DD-*-plan.md` | path matches | Format we know — generated by `/write-plan`. Steps map to user-story phases when they reference user-facing behaviour; otherwise to Foundational/Polish. Acceptance Criteria checklists become Acceptance Scenarios. |
| `docs/plans/YYYY-MM-DD-*-design.md` | path matches | Format we know — generated by `/brainstorm`. Maps strongly to spec.md (no plan.md content). |
| `*.md` | extension match | Generic markdown PRD. Apply heading mapping above. |
| Confluence URL | URL contains `atlassian.net/wiki/` | Requires Atlassian MCP. Fetch page; convert to markdown; apply heading mapping. |
| JIRA epic key (e.g., `PROJ-123`) | Argument matches `^[A-Z]+-\d+$` | Requires Atlassian MCP. Fetch the Epic and all child issues. Epic description → spec.md §Summary; each child issue with `Story` issuetype → User Story; each child with `Task` issuetype → tasks.md task; child Subtasks → indented under their parent task. |
| Directory containing multiple `.md` files | Path is a directory | Each file imported in alphabetical order; sections are merged when keys collide; merge conflicts get `[MERGE-CONFLICT]` flags. |

## Output Layout

After import, the spec directory contains:

```
specs/<NNN>-<slug>/
├── spec.md                         # populated from source
├── plan.md                         # populated from source (Technical Context + §1.x sections)
├── tasks.md                        # populated from source (with `[NEEDS REVIEW]` flags)
├── checklists/
│   └── requirements.md             # auto-generated from template (every item unchecked)
└── imported/
    ├── source-excerpts.md          # everything UNMAPPED, with original headings preserved
    ├── source-manifest.md          # which source path / URL produced which target section
    └── source-original/            # verbatim copy of the source file(s) for audit
```

**`source-manifest.md`** is the audit trail. Format:

```markdown
# Import manifest — <feature>

**Imported:** YYYY-MM-DD HH:MM
**Source:** <path or URL>
**Source content hash:** <sha256>
**Importer version:** spec-driven-development skill vX.Y.Z

## Mapping

| Source heading | Source path:line | Target | Bytes copied |
|----------------|-------------------|--------|--------------|
| ## Overview | docs/plans/2026-04-12-foo-plan.md:5 | spec.md §Summary | 412 |
| ## Requirements | docs/plans/2026-04-12-foo-plan.md:33 | spec.md §Functional Requirements | 1284 (12 FRs assigned FR-001..FR-012) |
| ## Risks | docs/plans/2026-04-12-foo-plan.md:120 | imported/source-excerpts.md ## Risks | 320 (UNMAPPED) |
```

This file enables a future `/spec import --reconcile` to detect when the source has changed and re-apply only the diff.

---

## Determinism Requirements

Two consecutive runs of `/spec import` against the same source file (with the same source content hash) MUST produce byte-identical `spec.md`, `plan.md`, `tasks.md`, and `imported/source-manifest.md` (modulo the `Imported:` timestamp line). If they don't, the importer has a bug.

Verification: on every import, the importer computes the SHA-256 of the produced artifacts and writes it to `imported/source-manifest.md`. A re-run on identical input must produce the same hashes.

---

## Post-Import Handoff

After import completes, the importer reports:

```
Imported <source> into specs/<NNN>-<slug>/
- spec.md: N user stories, M FRs, K SCs
- plan.md: <subsections populated>
- tasks.md: T tasks (S marked [NEEDS REVIEW])
- imported/source-excerpts.md: U unmapped sections
- requirements checklist: 0/N items checked

Recommended next: /spec specify --use-defaults  (apply defaults catalog where applicable)
                  /spec clarify                  (resolve [NEEDS CLARIFICATION] markers)
                  /spec challenge                (adversarial review)
                  /spec validate                 (gate to /execute-plan)
```
