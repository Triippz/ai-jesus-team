## Hooks system

### How Claude Code hooks work

Claude Code fires events at specific points during a session. Hooks are shell scripts that run in response to these events. The hook system is configured in `hooks/hooks.json`, which maps events to scripts.

There are three event types:

| Event | When it fires | What the hook receives on stdin |
|-------|--------------|-------------------------------|
| `SessionStart` | Session starts, resumes, or context is cleared | `{}` (empty JSON) |
| `PreToolUse` | Before a tool executes | `{"tool_input": {...}, "cwd": "..."}` |
| `PostToolUse` | After a tool executes | `{"tool_input": {...}, "cwd": "..."}` |

### The stdin/stdout contract

Every hook follows the same pattern:

```bash
#!/usr/bin/env bash
set -euo pipefail
INPUT=$(cat)                                          # Read JSON from stdin
COMMAND=$(echo "$INPUT" | jq -r '.tool_input.command // empty')  # Extract fields
# ... validation logic ...
exit 0   # Allow the operation
```

**Exit codes:**
- `0` — allow (operation proceeds)
- `2` — block (operation is cancelled, message shown to the AI)

**Output routing:**
- `stderr` — messages shown to the AI when blocking (e.g., `echo "BLOCKED: ..." >&2`)
- `stdout` — only used by SessionStart hooks to inject context (JSON with `hookSpecificOutput`)

### hooks.json structure

The config maps events to tool matchers, then to hook scripts:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": "${CLAUDE_PLUGIN_ROOT}/hooks/block-main-branch-commit-push.sh" }
        ]
      },
      {
        "matcher": "Edit|Write",
        "hooks": [
          { "type": "command", "command": "${CLAUDE_PLUGIN_ROOT}/hooks/protect-files.sh" }
        ]
      }
    ]
  }
}
```

**Matchers** filter which tool triggered the event:
- `Bash` — only fires when Claude runs a shell command
- `Edit|Write` — fires when Claude edits or creates a file
- `startup|resume|clear|compact` — fires on session lifecycle events

`${CLAUDE_PLUGIN_ROOT}` is replaced at runtime with the plugin's directory path.

### PreToolUse vs PostToolUse

**PreToolUse** hooks run *before* the operation. They can block it entirely (exit 2). This is used for:
- Preventing destructive commands (`block-destructive-git.sh`)
- Protecting sensitive files from edits (`protect-files.sh`)
- Scanning content *about to be written* for secrets (`detect-secrets.sh`)

**PostToolUse** hooks run *after* the operation completes. They can still exit 2 to flag issues, but the operation has already happened. This is used for:
- Checking the resulting file for secrets (`detect-secrets.sh` — runs on both pre and post)
- Warning about large diffs after a write (`warn-large-diff.sh`)
- Detecting AI test shortcuts in written test files (`detect-ai-test-shortcuts.sh`)

Notice that `detect-secrets.sh` appears in *both* PreToolUse and PostToolUse. On pre, it checks `tool_input.content` and `tool_input.new_string` (what's about to be written). On post, it reads the actual file from disk via `tool_input.file_path` to catch anything that slipped through.

### Hook implementation details

#### block-main-branch-commit-push.sh

**Purpose:** Block `git commit` and `git push` when the operation targets `main`/`master`. All other branches are unaffected.

**Logic flow:**
1. Extract `tool_input.command` via jq; ignore non-git-commit/push commands.
2. If `ALLOW_MAIN_BRANCH_COMMIT=1` is set in the environment → exit 0 (user-approved bypass).
3. If the command is `git push <remote> main|master` (by name) → exit 2.
4. Resolve the current branch via `git -C <cwd> symbolic-ref --short HEAD`.
5. If current branch is `main`/`master` and the command is `git commit` or `git push` → exit 2.
6. Otherwise → exit 0.

**Why this narrow scope:** feature branches should move freely; only direct commits or pushes to the protected branch require explicit user approval.

#### commit-msg-check.sh

**Purpose:** Enforce commit message format and block AI attribution.

**Logic flow:**
1. Only triggers on commands matching `git\s+commit.*-m` (commits with inline messages)
2. Extracts the message between quotes after `-m` using sed: `s/.*-m[[:space:]]*["']\([^"']*\)["'].*/\1/p`
3. Checks for AI attribution patterns (case-insensitive): `claude`, `anthropic`, `co-authored-by.*ai`, `generated by ai`, `ai-generated`
4. Validates format against: `^(feat|fix|docs|refactor|test|perf|build|ci|chore)(\(.+\))?\s*:\s*.+`

**Edge case:** If the sed extraction fails (e.g., message not in quotes), `COMMIT_MSG` is empty and the hook exits 0 — it won't block commands it can't parse. This is intentional: better to allow than to block legitimate commits with unusual quoting.

**macOS note:** The sed pattern uses `[[:space:]]` instead of `\s` because macOS BSD sed doesn't support `\s`.

#### block-unsafe-bash.sh

**Purpose:** Close the bash escape hatch — prevent using shell commands to bypass Edit/Write file protections.

**The problem it solves:** Without this hook, an AI could bypass `protect-files.sh` by running `sed -i 's/old/new/' .env` or `echo "SECRET=val" > .env` through the Bash tool instead of the Edit tool.

**Dual-condition pattern:** Most checks require *two* conditions to match:
1. A bypass method (`sed -i`, `python -c`, `echo ... >`)
2. A protected file pattern (`.env`, `.git/`, `*.key`, `*.pem`, etc.)

This means `sed -i s/old/new/ config.txt` is allowed (normal file), but `sed -i s/old/new/ .env` is blocked (protected file).

**Standalone blocks** (no dual condition needed):
- `rm -rf /` — always blocked (matches `rm\s+-rf\s+/\s*$`)
- `curl ... | bash` / `wget ... | sh` — always blocked
- `chmod 777` — always blocked
- `eval $variable` — always blocked (injection risk)

**Protected file patterns:** `\.env($|\..*)`, `\.git/`, `google-services\.json`, `GoogleService-Info\.plist`, `\.(secret|key|pem)$`

#### block-destructive-git.sh

**Purpose:** Block git operations that destroy work or bypass safety.

**Pre-filter:** The hook first checks if the command even contains git: `^\s*git\s|;\s*git\s|&&\s*git\s|\|\s*git\s`. Non-git commands exit 0 immediately. This prevents false positives on commands that happen to contain words like "reset" or "clean".

**Blocked operations:**
| Pattern | Why |
|---------|-----|
| `git reset --hard` | Discards all uncommitted changes |
| `git clean -f` | Permanently deletes untracked files |
| `git ... --no-verify` | Skips pre-commit hooks (safety bypass) |
| `git branch -D main\|master` | Deletes primary branches |
| `git push --force\|-f` | Rewrites remote history |
| `git checkout .` | Discards all uncommitted changes (the `$` anchor ensures `git checkout main` is allowed) |
| `git stash drop` | Permanently removes stashed work |

#### require-explicit-staging.sh

**Purpose:** Force explicit file names when staging — prevent accidentally staging sensitive files.

**Blocked:** `git add -A`, `git add --all`, `git add .` (with `$` anchor so `git add ./src/file.py` is allowed)

**Why:** `git add -A` could stage `.env` files, credentials, or other sensitive content. Requiring explicit file names forces intentional staging.

#### block-unsafe-sql.sh

**Purpose:** Block destructive SQL operations in bash commands.

**Case-insensitive matching:** The command is uppercased via `tr '[:lower:]' '[:upper:]'` before pattern matching.

**Blocked:**
- `DROP TABLE` / `DROP DATABASE` — permanent data loss
- `TRUNCATE` — deletes all rows
- `DELETE FROM ... ` without `WHERE` — the check looks for `DELETE\s+FROM\s+\S+\s+WHERE` and blocks if WHERE is missing

#### protect-files.sh

**Purpose:** Block Edit/Write operations on sensitive files.

**Reads:** `tool_input.file_path` (not command — this hooks into Edit/Write, not Bash)

**Protected patterns:**
| Pattern | Example matches |
|---------|----------------|
| `(^\|/)\.env($\|\..*)`| `.env`, `.env.local`, `.env.production`, `config/.env` |
| `(^\|/)\.git/` | `.git/config`, `.git/hooks/pre-commit` |
| `(^\|/)google-services\.json$` | `android/app/google-services.json` |
| `(^\|/)GoogleService-Info\.plist$` | `ios/Runner/GoogleService-Info.plist` |
| `\.(secret\|key\|pem)$` | `server.key`, `cert.pem`, `app.secret` |

#### protect-infrastructure.sh

**Purpose:** Block edits to infrastructure files that should be changed manually.

**Uses a deferred pattern:** Sets `BLOCKED` variable to a description, then checks at the end. This allows for readable error messages like "Cannot edit Dockerfile" vs "Cannot edit hook script".

**Protected files:**
- `.github/workflows/*.yml` — GitHub Actions
- `.gitlab-ci.yml` — GitLab CI
- `Dockerfile`, `docker-compose*.yml` — container configs
- `Makefile` — build system
- `hooks/*.sh`, `hooks/hooks.json` — hook scripts themselves
- `.claude-plugin/*.json` — plugin configuration

#### detect-secrets.sh

**Purpose:** Scan content for hardcoded secrets, API keys, tokens, and passwords.

**Three-tier content resolution:**
1. Try `tool_input.content` (Write tool — full file content)
2. Try `tool_input.new_string` (Edit tool — replacement text)
3. Try reading the file from `tool_input.file_path` (PostToolUse — file already written)

This cascading approach means the hook works for both pre-check (content/new_string available) and post-check (read the file).

**Detection patterns:**
| Pattern | What it catches |
|---------|----------------|
| `sk-[a-zA-Z0-9]{8,}` | OpenAI/Stripe secret keys |
| `pk_[a-zA-Z0-9]{8,}` | Stripe publishable keys |
| `AKIA[0-9A-Z]{16}` | AWS access keys |
| `ghp_...` / `gho_...` / `github_pat_...` | GitHub tokens |
| `Bearer [token]{20,}` | Bearer auth tokens |
| `password = "..."` | Hardcoded passwords |
| `secret = "..."` | Hardcoded secrets |
| `token = "..."` (8+ chars) | Hardcoded tokens |

**Placeholder allowlist:** Passwords matching `changeme`, `placeholder`, `xxx`, `your_password`, `TODO`, `REPLACE` are explicitly allowed. This prevents false positives in config templates and documentation.

#### warn-large-diff.sh

**Purpose:** Warn on large changes, block extremely large ones.

**Two measurement paths:**
1. **Git diff path** (preferred): If inside a git repo, runs `git diff --numstat -- "$FILE_PATH"` and sums insertions + deletions
2. **Fallback path**: For new files not yet in git, uses `wc -l` to count total lines

**Thresholds:**
- 500+ lines → WARNING (exit 0, message to stderr)
- 2000+ lines → BLOCKED (exit 2)

**Edge case with `set -euo pipefail`:** The `git diff --numstat` command can fail on files outside the git work tree. With `pipefail`, this propagates through the pipe to `awk`. The hook handles this by wrapping the git check in an `if git rev-parse --git-dir` guard, but the fallback path still runs for files in non-git locations.

#### detect-ai-test-shortcuts.sh

**Purpose:** Catch tests that don't actually test anything — a common AI pattern.

**File filter:** Only triggers on test files. Checks basename against: `^test_|_test\.|\.test\.|_spec\.`. Non-test files exit 0 immediately.

**Detection patterns:**
| Pattern | What it catches |
|---------|----------------|
| `assert True` / `assertTrue(True)` / `expect(true).toBe(true)` | Always-passing assertions |
| Test function with no `assert`/`expect`/`should`/`verify`/`check` in next 50 lines | Empty tests |
| `@skip` / `@unittest.skip` / `.skip()` | Skipped tests |
| `# TODO: assert` / `// TODO add assert` | Deferred assertions |

**No-assertion detection:** The hook greps for test function definitions (`def test_*`, `it(`, `test(`, `describe(`), then checks if the next 50 lines contain any assertion keyword. This is a heuristic — it limits to the first 5 functions and uses `break` to avoid O(n²) scanning.

#### session-start.sh

**Purpose:** Inject the `using-superpowers` skill into every session context.

**Output format:** Unlike all other hooks, this one writes to *stdout* (not stderr) and outputs structured JSON:

```json
{
  "hookSpecificOutput": {
    "hookEventName": "SessionStart",
    "additionalContext": "<EXTREMELY_IMPORTANT>...[skill content]...</EXTREMELY_IMPORTANT>"
  }
}
```

Claude Code reads this JSON and includes the `additionalContext` in the conversation context, making the skill available from the start of every session.

**Safe JSON encoding:** Uses `python3 -c` with `json.dumps()` to safely encode the SKILL.md file content (which can contain quotes, newlines, markdown, etc.) into a JSON string.

**Graceful degradation:** If `skills/using-superpowers/SKILL.md` doesn't exist, outputs a warning message instead of failing.

## install.sh

### Overview

An idempotent installer that reads a profile and configures Claude Code, Cursor, and Codex for a target project. It can be run repeatedly — second runs produce "already configured" messages with no side effects.

### Argument parsing

```
./install.sh [OPTIONS]

--profile <name>    Profile to install (required unless --list)
--dry-run           Preview changes without applying
--skip-tools        Skip tool installation (Step 1), config only
--target <path>     Override the target repository path from the profile
--list              List available profiles and exit
-h, --help          Show help and exit
```

The parser uses a `while [[ $# -gt 0 ]]` loop with `case` matching. Unknown options cause an immediate exit 1 with an error message.

### JSON parsing helpers

Two functions extract data from profile JSON files:

**`json_get <file> <key>`** — extracts a single value by dot-separated key path:
```bash
json_get "$PROFILE_FILE" "name"          # → "aok"
json_get "$PROFILE_FILE" "description"   # → "Nuv SaaS - Deno/Hono stack"
```

Uses `python3` as the primary parser (available on macOS and most Linux), with `jq` as a fallback. The Python implementation handles nested keys by splitting on `.` and walking the dict.

**`json_get_array <file> <key>`** — extracts an array as newline-separated values:
```bash
json_get_array "$PROFILE_FILE" "plugins"
# → core-superpowers
#   aok-fe-superpowers
```

### Profile structure

Profiles are JSON files in `profiles/` with this schema:
```json
{
  "name": "aok",
  "description": "Nuv SaaS - Deno/Hono stack",
  "plugins": ["core-superpowers", "aok-fe-superpowers"],
  "cursor_rules": ["shared", "shared-flutter", "aok"]
}
```

The `target_repo` field is optional (for backward compatibility with custom profiles). Built-in profiles omit it — the installer requires `--target` or prompts interactively.

All paths support `~` expansion — the installer replaces it with `$HOME` at runtime.

### Target resolution

The installer resolves the target repository path in this order:

1. `--target <path>` flag → use it (with tilde expansion)
2. `target_repo` field in profile → use it (backward compat for custom profiles)
3. If neither is provided and not dry-run:
   - Interactive terminal → prompt the user for the path (required, not optional)
   - Non-interactive → error out with clear message
4. If neither is provided and dry-run → use `<no target specified>` placeholder

If a target path is provided but the directory doesn't exist:
- Interactive terminal → warn and offer to correct the path
- Non-interactive → warn and continue with the provided path

### The four steps

#### Step 1: Tool installation

Installs Node.js, Claude Code, Codex, and checks for Cursor. Each tool:
1. Checks if already installed (`has_cmd`)
2. In dry-run mode, prints what would happen
3. Otherwise, installs via the best available method (Homebrew on macOS, apt/nvm on Linux)

Skipped entirely with `--skip-tools`.

#### Step 2: Claude Code configuration (the merge_plugins function)

This is the most complex step. It merges plugin paths into `~/.claude/settings.json` without overwriting existing configuration.

**How it works:**

1. Creates `~/.claude/` and `settings.json` if they don't exist
2. Calls `merge_plugins` — an embedded Python script that:
   - Reads the current `settings.json`
   - Maps plugin names to directory paths using a hardcoded mapping:
     ```python
     plugin_dir_map = {
         'aok-fe-superpowers': 'plugins/aok-fe',
         'aok-be-superpowers': 'plugins/aok-be',
         'atlas-superpowers': 'plugins/atlas-superpowers',
         'atlas-infra-superpowers': 'plugins/atlas-infra-superpowers',
     }
     ```
     `core-superpowers` maps to the repo root itself.
   - Looks up (or creates) `settings.projects.<target_repo>.plugins`
   - Adds any paths not already in the list (set-based dedup)
   - Sorts the final list and writes back

**Idempotency:** The set-based dedup means running twice with the same profile produces "already configured". The output reports `added:<path>` for each new plugin or `none` if nothing changed.

**Why reference-based:** Plugin paths point to directories in the dev-ai-utilities repo (e.g., `~/.dev-ai-utilities/plugins/aok-fe`). Claude Code reads the plugin's `.claude-plugin/plugin.json` at runtime. This means updating plugins is instant — just `git pull` the repo. No files are copied into the target project.

#### Step 3: Cursor rules

Calls `scripts/sync-cursor-rules.sh` with the target repo and rule set names from the profile.

**Graceful skip:** If the target repo doesn't exist yet, prints a warning and skips. This allows running the installer before cloning the target project — Step 2 (Claude Code config) still works.

#### Step 4: Codex configuration

Copies `.agents/skills/` and `AGENTS.md` from the dev-ai-utilities repo into the target project.

**Why copy-based:** Unlike Claude Code (which reads external plugin paths), Codex requires skill files to live inside the project directory. The installer diffs before copying to avoid unnecessary writes.

## kickstart.sh

### Purpose

A one-step clone-and-install script. Run it from inside the cloned repo to set up a profile in a single command.

**Note:** The repo is private behind GitLab SAML SSO, so `curl | bash` from raw URLs won't work. Clone the repo first, then run kickstart locally.

### Usage

```bash
cd ~/.dev-ai-utilities
./kickstart.sh --profile aok
./kickstart.sh --profile atlas --skip-tools
./kickstart.sh --list
```

### Flow

```
./kickstart.sh --profile aok
        │
        ▼
  Is ~/.dev-ai-utilities/.git present?
        │
    ┌───┴───┐
    │ YES   │ NO
    │       │
    ▼       ▼
  fetch +   Try SSH clone
  reset     ┌───┴───┐
  to HEAD   │ OK    │ FAIL
    │       │       │
    │       │       ▼
    │       │   Try HTTPS clone
    │       │       │
    ▼       ▼       ▼
  chmod all hooks executable
        │
        ▼
  exec install.sh "$@"
```

### SSH/HTTPS fallback

The script tries SSH first (`git@gitlab.com:...`), falling back to HTTPS (`https://gitlab.com/...`). This handles two common cases:
- Developers with SSH keys configured → SSH is faster and doesn't prompt for credentials
- CI environments or new setups without SSH keys → HTTPS works with access tokens

### Update mechanism

On subsequent runs, the script doesn't re-clone. It does `git fetch origin main` + `git reset --hard origin/main` to update to the latest version. This is a hard reset — intentional, because the local copy should always match the remote. Any local modifications to `~/.dev-ai-utilities` are discarded.

### Environment variables

| Variable | Default | Purpose |
|----------|---------|---------|
| `DEV_AI_UTILITIES_DIR` | `~/.dev-ai-utilities` | Where to clone/find the repo |
| `DEV_AI_UTILITIES_BRANCH` | `main` | Which branch to use |

### exec vs. bash

The final line uses `exec` instead of calling `install.sh` as a subprocess:
```bash
exec "$INSTALL_DIR/install.sh" "$@"
```

`exec` replaces the current shell process with install.sh, so the installer inherits the same PID and there's no parent shell waiting to resume.

## sync-cursor-rules.sh

### Purpose

Copies `.mdc` cursor rule files from dev-ai-utilities to a target repo's `.cursor/rules/` directory.

### Usage

```bash
scripts/sync-cursor-rules.sh <target_repo> <rule_dir1> [rule_dir2] ...
```

Example: `scripts/sync-cursor-rules.sh ~/Development/aok shared shared-flutter aok`

This copies all `.mdc` files from `cursor-rules/shared/`, `cursor-rules/shared-flutter/`, and `cursor-rules/aok/` into `~/Development/aok/.cursor/rules/`.

### Flow

```
Validate args (≥2 required)
        │
        ▼
Expand ~ in target path
        │
        ▼
Target exists? ──NO──▶ exit 1
        │
       YES
        │
        ▼
Cursor rules source exists? ──NO──▶ exit 1
        │
       YES
        │
        ▼
Rules dir already exists?
        │
    ┌───┴───┐
    │ YES   │ NO
    │       │
    ▼       ▼
  Scan for   mkdir -p
  changes    .cursor/rules/
    │            │
    ▼            │
  Any diffs? ◀───┘
    │
  ┌─┴─┐
  NO   YES
  │    │
  ▼    ▼
exit 0  Backup existing rules
"up to  (timestamp-named dir)
date"       │
            ▼
        Copy each .mdc file
        (skip if identical)
            │
            ▼
        Report: N synced,
        M already current
```

### Backup strategy

Before any file is modified, the entire existing `.cursor/rules/` directory is copied to `.cursor/rules.backup-YYYYMMDD-HHMMSS`. This provides a complete rollback point.

**Optimization:** The backup only happens if at least one file would actually change. The script pre-scans all source files against their targets using `diff -q`. If everything is identical, it prints "already up to date" and exits — no backup directory is created.

### Idempotency

Three layers of idempotency:
1. Pre-scan: if nothing changed, exit early (no backup created)
2. Per-file diff: individual files that are identical are skipped with "Already current"
3. `mkdir -p`: safe to call on an existing directory

## Test suite

### Framework: bats-core

[bats-core](https://github.com/bats-core/bats-core) (Bash Automated Testing System) — a TAP-compliant testing framework for bash. Vendored as git submodules so no global install is needed:

```
tests/
├── bats/                     # bats-core (git submodule)
└── test_helper/
    ├── bats-support/         # assertion support library (git submodule)
    └── bats-assert/          # assertion functions (git submodule)
```

First-time setup: `make install-test-deps` (runs `git submodule update --init --recursive`).

### Test helpers

#### common.bash

Loaded by every test file via `load '../test_helper/common'`.

**`run_hook <hook_path> <json_string>`** — the core helper. Pipes JSON to a hook script and captures exit code + merged stdout/stderr.

Implementation detail: uses `bash -c` with positional arguments to avoid quoting issues:
```bash
run bash -c 'printf "%s" "$1" | "$2" 2>&1' _ "$json_input" "$hook_path"
```

The `_` placeholder fills `$0` in the bash -c context, so `$1` gets the JSON and `$2` gets the hook path. This is critical because the JSON often contains `\"` (escaped quotes in JSON), which would be consumed by bash's double-quote expansion if passed through string interpolation. The single-quoted bash -c script avoids this entirely.

**JSON builders:**
- `make_bash_input <command> [cwd]` — builds `{"tool_input":{"command":"..."},"cwd":"..."}`
- `make_file_input <file_path>` — builds `{"tool_input":{"file_path":"..."}}`
- `make_content_input <content>` — uses `jq -n` for safe JSON encoding of arbitrary content
- `make_new_string_input <file_path> <new_string>` — uses `jq -n` for Edit tool simulation

**Temp dir management:** `setup_temp_dir` / `teardown_temp_dir` create and clean up an isolated temp directory per test via `mktemp -d`.

#### install_helper.bash

**`setup_install_env`** — creates a fake environment for install.sh tests:
- `$FAKE_HOME` — temp directory used as `$HOME`
- `$FAKE_TARGET` — temp directory simulating the target repo
- `$MOCK_BIN` — temp directory with mock executables (brew, node, npm, claude, codex, cursor) prepended to `$PATH`

The mock `node` script even handles `--version` to return `v20.0.0`, satisfying the installer's version check.

**`run_install <args>`** — runs install.sh with `HOME` set to the fake home.

### Test categories

#### Core hook tests (12 files, 120 tests)

Each hook gets its own `.bats` file with 5-15 tests covering:
- **Block path**: inputs that should exit 2 with "BLOCKED" in output
- **Allow path**: inputs that should exit 0
- **Edge cases**: empty input, missing fields, non-matching commands

Example test:
```bash
@test "blocks git push" {
  run_hook "$HOOK" '{"tool_input":{"command":"git push origin main"}}'
  assert_failure 2
  assert_output --partial "BLOCKED"
}
```

Tests that need real files (detect-secrets, warn-large-diff, detect-ai-test-shortcuts) use `setup_temp_dir` to create isolated temp files. The warn-large-diff tests create a temp git repo (`git init`) because the hook uses `git diff --numstat` internally, which fails on files outside a git work tree.

#### Plugin hook tests (3 files, 18 tests)

Representative tests for one hook per plugin:
- **aok-fe**: `protect-generated-dart.sh` — blocks `*.g.dart`, `*.freezed.dart`, `*.mocks.dart`, `*.gr.dart`
- **aok-be**: `protect-migrations.sh` — blocks `*/migrations/0*.py`
- **atlas-infra**: `block-terraform-destroy.sh` — blocks terraform destroy on production, warns on non-production

The atlas-infra test uses environment variable injection to test `CLAUDE_PROJECT_DIR` detection:
```bash
@test "blocks with CLAUDE_PROJECT_DIR set to prod" {
  CLAUDE_PROJECT_DIR="/projects/production/infra" run_hook "$HOOK" '...'
  assert_failure 2
}
```

#### Install tests (4 files, 13 tests)

- **argument_parsing.bats**: `--help`, `-h`, `--list`, unknown options, missing profile
- **json_helpers.bats**: Tests profile JSON parsing using python3 directly (avoids fragile function extraction from install.sh)
- **profile_validation.bats**: Nonexistent profile (exit 1), dry run with valid profile (exit 0)

#### Sync cursor rules tests (1 file, 5 tests)

Tests the actual `sync-cursor-rules.sh` script against temp directories:
- Too few args → exit 1
- Nonexistent target → exit 1
- First sync → files copied
- Second sync → "already up to date" (idempotent)

#### JSON validation (1 file, 3 tests)

Iterates all `.json` files in the repo (excluding `.git/`, `node_modules/`, vendored bats) and validates each with `python3 -m json.tool`.
