# Agent Catalog

Complete reference for all agents generated by the plugin template factory. Agents are rendered from Jinja2 templates in `templates/agents/` using a project profile.

---

## Team Agents

Team agents are the workflow backbone. They are generated once per plugin and coordinate the full development lifecycle.

### orchestrator

| Field | Value |
|---|---|
| Template | `templates/agents/team/orchestrator.md.j2` |
| Model | `claude-sonnet-4-6` |
| Role | Central workflow dispatcher and phase gatekeeper |

The orchestrator is the single entry point for all project work. It enforces the seven-step workflow order (brainstorm → plan → tdd → execute → review → verify → finish), reads changed files before making routing decisions, and gates progress between phases with mandatory human approval checkpoints.

**When it runs:** Every time work begins. The orchestrator never implements code or performs reviews itself — it delegates all execution to specialist agents.

**Key behaviors:**
- Reads the diff before selecting review agents (no hallucinated routing)
- Runs `spec-compliance-review` as the first gate before any other review agent
- Classifies tasks as trivial / standard / complex and scales the review suite accordingly
- Three-phase protocol: Research → Plan → Implement, with human gates between each

## Review Agents

Ten specialist review agents, each with a single focused responsibility. All agents output a uniform JSON envelope conforming to `schemas/review-output.schema.json`.

### complexity-review

| Field | Value |
|---|---|
| Template | `templates/agents/review/complexity-review.md.j2` |
| Model | `claude-haiku-4-5` |
| Checks | Function length, cyclomatic complexity, nesting depth, parameter count |

Measures structural complexity against per-language thresholds. Uses profile-defined overrides when `profile.review_thresholds` is set; otherwise falls back to language defaults.

**Language thresholds (defaults):**

| Language | Max lines | Max CC | Max depth | Max params |
|---|---|---|---|---|
| Rust | 50 | 10 | 4 | 5 |
| Python | 20 | 10 | 4 | 5 |
| Dart | 30 | 10 | 4 | 5 |
| Go | 50 | 15 | 3 | 5 |
| TypeScript | 25 | 10 | 4 | 4 |

**Stack-specific tailoring:**
- Rust: `&self`/`&mut self` excluded from parameter count; `match` arms each count as a CC branch
- Python: blank lines and docstrings excluded from function length; `self`/`cls` excluded from param count
- Dart: widget build methods flagged as suggestions (not errors) up to depth 6; named params with defaults noted at lower severity
- Go: receiver params excluded; `if err != nil` at depth 2 may be warning rather than error
- TypeScript: destructured object params count as 1; ternary operators count as CC branches

**Skip condition:** No code files in target; all files are generated or vendored (`*.g.dart`, `*.pb.go`, `node_modules/`, `target/`); documentation-only target.

**Ignore list:** Naming conventions, domain modeling, security, test quality, documentation, import organization, performance, style formatting.

### concurrency-review

| Field | Value |
|---|---|
| Template | `templates/agents/review/concurrency-review.md.j2` |
| Model | `claude-sonnet-4-6` |
| Checks | Race conditions, deadlocks, thread safety, async correctness, resource lifecycle, cancellation propagation |

Reviews all async, concurrent, and parallel code patterns. Applies high scrutiny — flags ambiguous patterns at `confidence: medium` rather than silently passing.

**Stack-specific tailoring:**
- Rust: `Arc<Mutex<T>>` held across `.await`, lock ordering for AB/BA deadlocks, `tokio` vs `std` sleep, SQLite `BEGIN IMMEDIATE` held across I/O, ractor actor blocking
- Python: asyncio lock context manager usage, Celery task atomicity/idempotency, Django Channels state management, Redis pipeline races, GIL implications for CPU-bound threads
- Dart: event loop interleaving between `await` points, `StreamController` lifecycle, `Stream` subscription semantics, isolate `SendPort` safety, Flutter `setState`-after-`dispose`
- Go: goroutine loop variable closure (pre-1.22), map concurrent access, `sync.WaitGroup.Add` placement, `defer` in loops, `context.Done` in long-running loops
- TypeScript: `await` in `forEach`, `Promise.all` side-effect ordering, `Promise.race` without cancellation, event loop blocking, Deno `postMessage` clone cost

**Skip condition:** No async, concurrent, or parallel code patterns detected (no async keywords, no goroutines, no threading imports, no concurrency primitives). Documentation or pure configuration targets also skip.

**Ignore list:** Naming, complexity metrics, domain modeling, documentation, import organization, test structure.

---

### doc-review

| Field | Value |
|---|---|
| Template | `templates/agents/review/doc-review.md.j2` |
| Model | `claude-sonnet-4-6` |
| Checks | README accuracy, inline doc comment accuracy, CHANGELOG entries, misleading comments, public API documentation completeness |

Verifies that written documentation reflects the code as it actually exists. A doc comment block in any changed source file counts as documentation.

**Stack-specific tailoring:**
- Rust: `///` rustdoc required on all `pub` items; `# Errors` required on `Result`-returning functions; `# Panics` required when panic is possible
- Python: docstrings with `Args:`/`Returns:`/`Raises:` sections on all public functions; parameter lists must match signatures exactly
- Dart: `///` dartdoc with `[paramName]` syntax; `@param` tags must be accurate if present
- Go: godoc comments must begin with the exported identifier name; package-level comments before the `package` declaration
- TypeScript: JSDoc `/** */` with `@param`, `@returns`, `@throws` on all exports; `@param` referencing a non-existent parameter is an error

**Skip condition:** No `.md` files and no structured doc comment blocks in any changed source files.

**Ignore list:** Naming quality, algorithmic complexity, domain correctness, security, test coverage, code style, architectural decisions.

---

### domain-review

| Field | Value |
|---|---|
| Template | `templates/agents/review/domain-review.md.j2` |
| Model | `claude-opus-4-7` |
| Checks | Anemic domain models, boundary violations, DDD pattern health (aggregates, value objects, domain events, repositories), cross-context coupling |

Requires deep semantic understanding of business concepts. Only evaluates files containing domain or business logic — skips infrastructure, configuration, migration, and test files.

**Stack-specific tailoring:**
- Rust: domain structs importing from `infrastructure` modules; Diesel models mixed with domain logic; sqlx raw rows returned without mapping to domain types
- Python: business logic in DRF serializers; Django model managers performing domain operations; direct ORM usage in views; Celery tasks containing business rules
- Dart: BLoC event handlers containing domain logic; Drift DAOs performing business operations; `BuildContext` passed into service classes
- Go: HTTP handlers containing business rules; repository implementations performing domain validation; domain structs imported by infrastructure packages
- TypeScript: controllers performing domain operations; Supabase RLS policies without corresponding domain enforcement; service classes constructing HTTP responses

**Skip condition:** No domain or business logic files in target; infrastructure/configuration/migration/test files only; codebase does not apply DDD patterns (a simple CRUD service is not penalized for lacking a domain layer).

**Ignore list:** Naming conventions, complexity metrics, concurrency, documentation, test structure, security, performance, import style.

### naming-review

| Field | Value |
|---|---|
| Template | `templates/agents/review/naming-review.md.j2` |
| Model | `claude-haiku-4-5` |
| Checks | Convention violations, naming consistency within files, magic values, misleading names |

**Stack-specific tailoring (convention tables):**
- Rust: `snake_case` functions/variables, `PascalCase` structs/enums/traits, `SCREAMING_SNAKE_CASE` constants; compiler-enforced violations are suggestions, not warnings
- Python (PEP 8): `snake_case` functions/variables, `PascalCase` classes, `UPPER_CASE` module-level constants; dunder methods and Django model fields exempt
- Dart (Effective Dart): `lowerCamelCase` functions/variables/constants (not SCREAMING_SNAKE), `UpperCamelCase` classes/enums, `lowercase_with_underscores` files
- Go: `PascalCase` exported, `camelCase` unexported, acronyms all-caps (`userID`, `HTTPClient`), no `ALL_CAPS` constants, single-letter short-scope variables exempt
- TypeScript: `camelCase` functions/variables, `PascalCase` classes/interfaces/types, no `I` prefix on interfaces, React components must be `PascalCase`

**Magic value rule:** Numbers other than 0, 1, -1, 2 in arithmetic/comparisons without a named constant; string literals used as status codes, routing keys, or config keys without a constant or enum. Magic values in tests are exempt.

**Skip condition:** No code files in target; all files are auto-generated; configuration or documentation only.

**Ignore list:** Function length, domain modeling, security, test structure, import organization, performance, linting-enforced formatting.

### performance-review

| Field | Value |
|---|---|
| Template | `templates/agents/review/performance-review.md.j2` |
| Model | `claude-haiku-4-5` |
| Checks | N+1 query patterns, unbounded result sets, quadratic algorithms in hot paths, large object copies in tight loops |

**Stack-specific tailoring:**
- Rust: unnecessary `.clone()` on `Copy` types; `Box<T>` for known-size types; `Arc` in single-threaded code; intermediate `.collect()` then `.iter()` chains; `format!()` in hot loops
- Python: N+1 ORM queries (`select_related`/`prefetch_related` missing); synchronous I/O in `async def` without `sync_to_async`; queryset re-evaluation; list comprehension where generator suffices
- Dart: unnecessary `setState` rebuilds; missing `const` constructors; `StreamSubscription` without `cancel()` in `dispose()`; side effects in `build()` methods
- Go: `make` at size 0 inside loops; goroutine leaks from unbounded channel reads; missing context cancellation propagation; `append` without pre-allocation; `defer` in loops for resource-heavy calls
- TypeScript: object/array literals as props on every render without memoization; synchronous `readFileSync` in request handlers; DOM thrashing; `Array.find` inside loops where a `Map` would be O(1); unthrottled scroll/resize listeners

**Skip condition:** No code files in target (configuration, markdown, or asset files only).

**Ignore list:** Naming, domain correctness, security, test quality, documentation, architectural decisions.

### progress-guardian

| Field | Value |
|---|---|
| Template | `templates/agents/review/progress-guardian.md.j2` |
| Model | `claude-haiku-4-5` |
| Checks | Repeated errors (3+), same-approach retries, growing file count without tests, scope creep during execution, context exhaustion signals |

**Special behavior:** This agent reviews the _process_ of agent execution, not code artifacts. It never skips. If invoked with no session data, it returns `pass`.

**Escalation trigger:** Any `error`-severity finding causes the summary to end with `ESCALATION RECOMMENDED: Human intervention or agent restart advised.`

**Thresholds:**
- 3 identical errors with no approach change → `warning`; 5+ → `error`
- Same tool call sequence repeated twice → `warning`; 4+ times → `error`
- 5+ new source files with no new test files → `warning`; 10+ → `error`
- Session transcript > 80 tool call round-trips → `warning`; > 120 → `error`

**Skip condition:** None. This agent always runs.

**Ignore list:** All code-level concerns (correctness, naming, security, performance, test quality, domain modeling).

---

### spec-compliance-review

| Field | Value |
|---|---|
| Template | `templates/agents/review/spec-compliance-review.md.j2` |
| Model | `claude-sonnet-4-6` |
| Checks | Functional requirement coverage, acceptance scenario coverage, scope creep detection, requirement-to-file traceability |

**This agent is always the first gate.** If it returns `fail`, the orchestrator halts the review chain before running any other agent.

Parses `spec.md` at the repo root for labeled requirements (`FR-NNN`, `REQ-NNN`, `MUST`, `SHALL`), user stories, and BDD scenarios (`Given/When/Then`). Flags unimplemented in-scope requirements as `error`; deferred requirements as `warning`; scope creep (new APIs, dependencies, config keys not in spec) as `warning` or `suggestion`.

**Skip condition:** `spec.md` not found in the repository. Returns `skip` immediately.

**Ignore list:** Code quality, naming, performance, security, test assertion patterns, documentation, architectural decisions.

### structure-review

| Field | Value |
|---|---|
| Template | `templates/agents/review/structure-review.md.j2` |
| Model | `claude-sonnet-4-6` |
| Checks | Separation of concerns, test mirroring, single responsibility per module, dead directories |

**Universal checks (all stacks):** Cross-layer leakage (raw SQL in view handler, HTTP response construction in model), test file mirroring, modules mixing unrelated concerns, empty directories.

**Stack-specific tailoring:**
- Rust: crate boundary decomposition, module file style consistency (`mod.rs` vs file-per-module), test location (`#[cfg(test)]` vs `tests/`), workspace `Cargo.toml` layout, `lib.rs` vs `main.rs` entry points
- Python: Django app structure, `__init__.py` presence (missing is `error`), test mirroring, settings split (`base/local/production`), business logic not in views or serializers
- Dart: melos monorepo `pubspec.yaml` presence (missing is `error`), `lib/` atomic design tier organization, feature-first vs atomic design consistency, test mirroring, platform directory purity
- Go: `cmd/`/`internal/`/`pkg/` standard layout, `internal/` enforcement, test colocation with package, `main` package isolation, package name matches directory name (mismatch is `error`)
- TypeScript: `src/` structure, module organization (`routes.ts`/`controller.ts`/`service.ts`), routes vs controllers vs services separation, test mirroring, barrel files (`index.ts`) must not contain logic

**Skip condition:** Fewer than 3 files in the review target.

**Ignore list:** Naming quality, algorithmic complexity, domain correctness, security, test quality/assertions, code style, dependency versions, documentation accuracy.

### test-review

| Field | Value |
|---|---|
| Template | `templates/agents/review/test-review.md.j2` |
| Model | `claude-sonnet-4-6` |
| Checks | Farley Score (8 weighted properties from Dave Farley's _Modern Software Engineering_) |

Evaluates each test function against 8 properties, computes a weighted score per test and per file, and reports issues by Farley Score band.

**Farley Score properties and weights:**

| Property | Weight | Signals of low score |
|---|---|---|
| Specificity | 1.5 | Multiple unrelated asserts, test name describes scenario but verifies 3+ behaviors |
| Independence | 1.5 | Shared mutable state, order-dependent tests, missing teardown |
| Repeatability | 1.0 | `datetime.now()` without mock, random without seed, external network calls, `sleep` for timing |
| Self-Validating | 1.0 | `print` in place of assertions, test passes by not throwing, commented-out assertions |
| Timely | 0.5 | New production code with no new tests, tautological tests |
| Fast | 0.5 | `sleep` with fixed duration, full server spin-up for unit assertions |
| Focused | 1.0 | Over-configured setup blocks, deep nesting of describe/context, over-mocking |
| Maintainable | 1.0 | Tests break on internal changes (public interface unchanged), magic values, copy-paste |

**Score thresholds:** < 5.0 → `error`; 5.0–7.0 → `warning`; 7.0–8.5 → `suggestion`; ≥ 8.5 → pass.

**Stack-specific tailoring:** Recognizes language-specific test patterns (Rust `#[test]`/`#[tokio::test]`, Python `pytest`/`unittest`, Dart `test()`/`testWidgets()`, Go `_test.go` table-driven, TypeScript `Deno.test`/`describe`/`it`).

**Skip condition:** No test files in target; only production code with no tests directory; documentation or configuration only.

**Ignore list:** Naming conventions in test functions (exempt), production code complexity, domain modeling, security, concurrency in production code, documentation quality.

## Plan Review Personas

Four personas review implementation plans in parallel before execution begins. They use a different output schema from code review agents: `verdict` (`approve`/`needs-revision`) and `issues` with `severity` (`blocker`/`warning`).

**Common verdict rule:** any `blocker` → `needs-revision`; 3+ `warning` with no blockers → `needs-revision`.

### Acceptance Test Critic (plan-review-acceptance)

| Field | Value |
|---|---|
| Template | `templates/prompts/plan-review-acceptance.md.j2` |
| Model | `claude-haiku-4-5` |
| Role | Test-first rigor gate |

Challenges: every acceptance criterion must be independently verifiable (Given/When/Then with measurable outcome); every user story must have at least one identifiable test task; test tasks must precede implementation tasks; error paths must be covered; BDD scenarios must cover happy path, boundary condition, and failure condition.

**Unique output fields:** `missing_scenarios` — an array of draft Gherkin (or equivalent framework) scenarios for missing error paths and boundary conditions, even when verdict is `approve`.

**Blocker examples:** user story with no test task; acceptance criterion with vague outcome ("the system handles errors gracefully"); implementation task appearing before its test task in the sequence.

**Does not self-skip:** If the plan contains no explicit user stories, emits a blocker for every implementation task without a corresponding test task.

---

### Design & Architecture Critic (plan-review-design)

| Field | Value |
|---|---|
| Template | `templates/prompts/plan-review-design.md.j2` |
| Model | `claude-haiku-4-5` |
| Role | Structural integrity gate |

Challenges: circular dependencies (direct or transitive), business logic in controllers/handlers/views, domain modules importing infrastructure, God objects (> 400 lines or multiple major concerns), one-to-one abstractions with no flexibility rationale.

**Language-specific checks:** Rust crate dependency direction (app → domain → utility); Python circular imports as runtime errors and service layer isolation; Dart widget/BLoC/repository responsibility; Go package naming, interface segregation, handler purity; TypeScript module barrel API, constructor injection, controller purity.

**Blocker examples:** circular dependency between any two modules; business logic in a handler; domain module importing infrastructure; module handling more than one major concern and exceeding 400 lines.

---

### Strategic Critic (plan-review-strategic)

| Field | Value |
|---|---|
| Template | `templates/prompts/plan-review-strategic.md.j2` |
| Model | `claude-haiku-4-5` |
| Role | Problem-solution fit and risk gate |

Challenges: clear problem statement (specific, observable, with measurable impact); root cause vs symptom treatment; right-sized scope; irreversible changes with rollback plans; opportunity cost acknowledgment for large investments (> 3 engineering-days).

**Unique output field:** `scope_assessment` — classifies current scope (small/medium/large), recommends appropriate scope, identifies whether the plan could be split, and describes the minimum viable subset.

**Blocker examples:** no identifiable problem statement; solution clearly treats symptom while root cause is identifiable; irreversible change (DB migration, data transformation, external API contract, auth model change) with no rollback strategy; dependency/framework disproportionate to the problem with no rationale.

---

### UX Critic (plan-review-ux)

| Field | Value |
|---|---|
| Template | `templates/prompts/plan-review-ux.md.j2` |
| Model | `claude-haiku-4-5` |
| Role | User experience quality gate |

Challenges: error state recovery paths (every failure must have a described user-facing outcome); destructive action confirmation (delete, archive, cancel, reset, batch operations); keyboard navigation plan for every interactive element; user journey completeness (entry point to terminal state); cognitive load (max 7 ± 2 choices per screen).

**Language-specific accessibility checks:**
- Dart/Flutter: `Semantics` widget wrapping, `AlertDialog` for destructive actions, focus management for modals, 48×48 dp touch targets
- TypeScript/Web: ARIA roles/states/properties, WCAG 2.1 AA contrast (4.5:1 normal text), focus trapping in modals, `aria-describedby` for form errors

**Self-skip:** If no user story mentions UI-facing terms (screen, form, button, input, modal, etc.), returns `{"verdict": "approve", "issues": [], "skipped": true}` without further analysis.

**Blocker examples:** error state with no user-facing recovery; destructive action with no confirmation; user journey with no terminal state described.

## Model Routing Table

| Tier | Model | Agents | Rationale |
|---|---|---|---|
| Haiku | `claude-haiku-4-5` | complexity-review, naming-review, performance-review, progress-guardian, plan-review-acceptance, plan-review-design, plan-review-strategic, plan-review-ux | Structural and mechanical checks; fast and cheap; patterns are deterministic |
| Sonnet | `claude-sonnet-4-6` | concurrency-review, doc-review, spec-compliance-review, structure-review, test-review, orchestrator | Quality and spec gates requiring reasoning about intent and context |
| Opus | `claude-opus-4-7` | domain-review | Deep semantic reasoning about business domain; bounded context analysis requires understanding organizational intent |

The orchestrator can override the default tier only when the diff involves business-critical logic and the user explicitly requests a deeper pass. Tier does not affect health score weight — a warn from Haiku carries the same weight as a warn from Opus.

## Dispatch Rules

The orchestrator determines which review agents to run by reading the changed file set and matching against this table. When multiple categories match, the agent sets are unioned.

| Changed file category | Agents dispatched |
|---|---|
| Any change (baseline) | spec-compliance-review (first gate) + structure-review |
| Code files | spec-compliance-review, structure-review, complexity-review, naming-review |
| Test files | test-review |
| API / auth surface (routes, middleware, auth handlers) | spec-compliance-review, structure-review |
| Domain / business logic (models, services, use-cases) | domain-review (Opus), spec-compliance-review |
| Concurrency / async code (futures, goroutines, async/await, actors) | concurrency-review |
| Performance-critical paths (hot loops, caching, batching) | performance-review |
| Documentation only | doc-review |

**File-type detection patterns (per language):**

| Language | Code files | Test files | Skip (generated) |
|---|---|---|---|
| Rust | `*.rs` | `#[cfg(test)]` or `tests/` | `*.g.rs`, `*_generated.rs`, `build.rs` |
| Python | `*.py` | `test_*.py`, `*_test.py`, `tests/` | `migrations/`, `*_pb2.py`, `*.generated.py` |
| Dart | `*.dart` | `*_test.dart`, `test/`, `integration_test/` | `*.g.dart`, `*.freezed.dart`, `*.mocks.dart` |
| Go | `*.go` | `*_test.go` | `*.pb.go`, `*_gen.go` |
| TypeScript | `*.ts`, `*.tsx` | `*.test.ts`, `*.spec.ts`, `tests/`, `__tests__/` | `*.d.ts` |

**Complexity routing override:**

| Complexity | Criteria | Review suite |
|---|---|---|
| Trivial | Single-file change, no logic, no API surface (doc fix, config tweak) | structure-review only |
| Standard | Logic changes, new functions, refactoring, test additions | spec-compliance-review gate + dispatch table agents |
| Complex | New features, API surface changes, domain model changes, cross-cutting | Full suite including domain-review at Opus tier |

When in doubt, treat as **standard**. Never downgrade to trivial without explicit justification.
